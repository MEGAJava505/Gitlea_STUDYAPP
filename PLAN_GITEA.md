# 1. PRODUCT VISION

Local GitHub — единая образовательная веб-платформа для изучения программирования и работы с реальными Git-репозиториями.

Платформа объединяет:

- Управление студентами и учебными группами.
- Библиотеку курсов.
- Учебные материалы.
- Практические задания.
- Работу с Git.
- Code Review.
- Оценивание.
- Уведомления.
- Администрирование.

Gitea используется как внутренний Git-движок. Пользователь должен воспринимать Local GitHub как один цельный продукт.

## 1.1. Первая аудитория

MVP предназначен для JDU:

- Одна группа Sun'iy Intellekt.
- Ориентировочно 28 студентов.
- Один преподаватель.
- Один создатель системы, который одновременно является студентом.

Поддержка нескольких групп и преподавателей предусматривается в модели данных и правах, но массовое внедрение не входит в первоначальную цель.

## 1.2. Критерий успеха

Преподаватель способен самостоятельно:

1. Добавить студентов.
2. Создать курс.
3. Загрузить материалы.
4. Опубликовать задание.
5. Получить Git-работы.
6. Проверить код.
7. Выставить результат.

Студент проходит весь процесс без помощи разработчика.

# 2. ПРИНЦИПЫ РАЗРАБОТКИ

1. Local GitHub — адаптивная веб-платформа.
2. Вся собственная прикладная логика пишется на TypeScript.
3. Не переписываем функции, уже предоставляемые Gitea.
4. Не создаём отдельную нативную мобильную программу.
5. Придерживаемся минималистичного UX/UI.
6. Не вводим дополнительные роли, экраны и процессы без конкретной необходимости.
7. Все критические операции проверяются на сервере.
8. Для будущего масштабирования оставляем разумную архитектуру, но не строим его заранее.

## Рассмотренные архитектурные подходы

**Подход A:** раздельная LMS + Gitea с переходами между интерфейсами. Отклонён — не соответствует требованию единого продукта.

**Подход B:** полностью собственная реализация Git-платформы. Отклонён из-за высокой трудоёмкости и дублирования существующих решений.

**Подход C:** собственная образовательная веб-платформа с глубоко интегрированной Gitea.

**Выбран подход C.**

# 3. ПОЛЬЗОВАТЕЛИ И РОЛИ

Роли являются комбинируемыми. Один пользователь может иметь несколько ролей одновременно.

## 3.1. Student

Доступ к своим курсам, материалам, заданиям, репозиториям, результатам и настройкам.

## 3.2. Teacher

- Создание собственных курсов.
- Использование общих курсов.
- Управление обучением назначенных групп.
- Публикация материалов и заданий.
- Проверка работ.
- Комментарии и оценивание.
- Просмотр прогресса.

## 3.3. Admin

- Управление пользователями.
- Импорт студентов.
- Управление группами.
- Управление административными правами в пределах полномочий.
- Настройки платформы.
- Журнал действий.

Admin не может самостоятельно назначить себе роль Owner.

## 3.4. Owner

Владелец системы с полными полномочиями управления её инфраструктурой и административной конфигурацией.

Может назначать и отзывать Admin. Нельзя случайно удалить последнего Owner.

## 3.5. Начальная конфигурация

**Создатель:**

- Student.
- Owner.

**Преподаватель:**

- Teacher.
- При необходимости получает Admin от Owner.

**Остальные:**

- Student.

Дополнительные аккаунты для совмещения ролей не создаются.

## 3.6. Две панели

У пользователя одна учётная запись, но два рабочих пространства при наличии соответствующих ролей.

Например:

- Student Panel / Admin Panel.
- Teacher Panel / Admin Panel.

Переключение выполняется без повторного входа.

Это не две независимые системы авторизации. Backend проверяет права каждого действия независимо от выбранного интерфейса.

## 3.7. Разделение академических и системных полномочий

Наличие Owner или Admin не должно автоматически разрешать пользователю оценивать собственные задания.

Для MVP устанавливаем:

- Проверка собственных работ запрещена через пользовательские и административные API.
- Изменение собственной оценки запрещено.
- Академическое оценивание выполняет назначенный преподаватель.
- Все административные изменения результатов журналируются.
- Скрытые тесты не отображаются в Student Panel и обычной Admin Panel.

Владелец физического сервера технически может обладать более широким инфраструктурным доступом. Программные ограничения не являются гарантией независимого академического аудита от владельца сервера.

# 4. REGISTRATION & AUTHENTICATION

## 4.1. Подготовка аккаунтов

Администратор импортирует официальный университетский список студентов.

Для каждой записи используются:

- Student ID.
- Имя.
- Фамилия.
- Группа.
- Ожидаемый университетский email.
- Статус активации.

До импорта система проверяет дубликаты и корректность идентификаторов.

## 4.2. Регистрация через общий QR

Последовательность:

1. Преподаватель показывает один QR-код всей группе.
2. Студент сканирует его.
3. Открывается страница активации Local GitHub.
4. Студент вводит университетский email.
5. На почту отправляется одноразовая ссылка.
6. Студент подтверждает владение почтой.
7. Вводит Student ID.
8. Система сверяет ID, email и запись импортированного списка.
9. При совпадении активируется учётная запись.
10. Студент получает автоматически созданные логин и пароль.

QR открывает процесс активации группы, но сам по себе не подтверждает личность.

QR и ссылки имеют сроки действия и могут быть отозваны администратором.

Повторная активация уже существующего аккаунта запрещена. Система фиксирует конфликтные попытки.

## 4.3. Университетский email

Для обычных студентов используется согласованная модель:

`Student ID + первая буква имени + @jdu.uz`

Ожидаемый email рассчитывается при импорте и сохраняется в записи студента.

Если официальный адрес является исключением из шаблона, Admin может исправить его до активации, предварительно проверив принадлежность.

Для Staff и Teacher email не генерируется по студенческому шаблону — используется подтверждённый адрес.

## 4.4. Логин

Формат:

`jdu-<StudentID>`

Пример: `jdu-2400051`.

У одного Student ID не может быть нескольких обычных аккаунтов.

## 4.5. Автоматический пароль

Согласованное первоначальное значение:

- Ровно семь символов.
- 4 случайные строчные латинские буквы и 3 цифры либо 3 буквы и 4 цифры.
- Оба варианта выбираются случайно.
- Порядок символов полностью перемешивается.
- Используется криптографически стойкая генерация.
- Полные выдаваемые значения не повторяются между пользователями.

Для проверки повторов допускается хранение отдельного защищённого HMAC-отпечатка выдаваемого пароля; открытый пароль не сохраняется в образовательной базе.

После активации пароль показывается один раз на защищённой странице.

Добровольная смена доступна в настройках. Обязательной смены при первом входе нет.

Восстановление доступа — через подтверждённую университетскую почту. Старый пароль пользователю не раскрывается.

## 4.6. Единый вход с Gitea

Целевая схема MVP:

- Gitea обслуживает Git-учётную запись и выступает OAuth2/OIDC-провайдером.
- Образовательная часть связывает внешний стабильный идентификатор Gitea с внутренней записью пользователя.
- Первоначальное создание аккаунтов выполняется серверной логикой после проверки QR-регистрации.
- У пользователя одна пара основных учётных данных для веб-входа.
- Права Student, Teacher, Admin и Owner определяются образовательной платформой, а не наличием прав администратора Gitea.

Изменение пароля и восстановление должны синхронно обновлять основной источник учётных данных.

Вход в Gitea оформляется под Local GitHub. Внешний Git-доступ через терминал использует SSH-ключи или ограниченные Git-токены, а не пароль, встроенный в Clone URL.

**Техническая проверка до реализации:** протестировать создание пользователя, первый вход, OIDC redirect, выход, восстановление доступа, смену пароля и работу Git по SSH/HTTPS.

Если выбранная конфигурация не обеспечивает единый вход без противоречий, полноценная разработка авторизации не начинается до уточнения схемы.

## 4.7. Защита авторизации

Обязательны:

- Ограничение попыток входа по аккаунту и источнику запроса.
- Защита от распределённого перебора в пределах доступных механизмов.
- Одинаковые внешние сообщения для чувствительных ошибок активации.
- Безопасные cookie и серверные сессии.
- Защита от CSRF.
- Ограниченный срок действия одноразовых ссылок.
- Аннулирование использованных приглашений.
- Проверка административных прав при каждом запросе.
- Журнал подозрительных попыток входа.

**2FA не входит в согласованный MVP.**

Семизначный постоянный пароль является сознательным отклонением от современных рекомендаций по стойкости. Даже с ограничениями попыток сохраняется остаточный риск, в том числе при компрометации базы хешей.

# 5. GROUP MANAGEMENT

## 5.1. Источник данных

Первоначально группы импортируются из Google Sheets.

Основной сценарий:

Google Sheets → Export XLSX/CSV → Import в Local GitHub.

Постоянная двусторонняя синхронизация с Google API для MVP не нужна.

## 5.2. Импорт

До подтверждения импорта показывается предпросмотр:

- Новые студенты.
- Уже существующие студенты.
- Изменённые данные.
- Дубликаты.
- Ошибочные строки.

Сопоставление выполняется по Student ID.

Повторный импорт не должен удалять аккаунты, репозитории и выполненные задания только потому, что студент исчез из таблицы.

## 5.3. Ручное редактирование

Администратор может изменять состав группы вручную.

Преподаватель с соответствующими полномочиями может корректировать участие студентов в своих курсах, не меняя официальный реестр группы.

## 5.4. Назначение курса

Когда группе назначается курс, её текущие участники получают доступ автоматически.

Индивидуальное добавление или исключение студента из конкретного курса допускается.

# 6. COURSE LIBRARY

## 6.1. Общая библиотека

Курс существует в единственном экземпляре и может использоваться несколькими преподавателями и группами.

Содержит:

- Название и описание.
- Уроки.
- Материалы.
- Общие задания.
- Стартовые проекты.

## 6.2. Course Ownership

Редактировать оригинальные материалы могут:

- Автор курса.
- Admin.
- Owner при наличии административных полномочий.

Другие преподаватели могут использовать курс, но не изменять оригинал.

## 6.3. Публикация

Преподаватель постепенно открывает уроки своей группе.

Открытие урока для группы A не открывает его автоматически группе B.

Обновления обычных учебных материалов автора применяются к общей библиотеке без отдельной системы Course Versioning.

При этом уже зафиксированные условия сдачи, результат и commit SHA не могут изменяться задним числом. Стартовый проект, выданный студенту, также не перезаписывается обновлением общего шаблона.

## 6.4. Дополнительные задания

Преподаватель, использующий чужой курс, может создать отдельное задание только для собственной группы.

Такое задание не изменяет общий курс.

# 8. GIT ARCHITECTURE

## 8.1. Выбранная модель

**Один приватный Git-репозиторий на студента и задание.**

Это окончательно выбранный вариант MVP.

Пример:

`local-github/assignment-04-jdu-2400051`

При создании задания преподаватель прикрепляет стартовый проект или выбирает существующий Git-шаблон.

Local GitHub через Gitea API создаёт каждому студенту независимый приватный репозиторий.

Шаблоны используются вместо обязательной Fork-модели.

## 8.2. Владение и доступ

Репозитории принадлежат служебной организации Local GitHub, а не студентам.

Студент получает Write-доступ только к своему репозиторию.

Он не является владельцем или администратором репозитория.

Преподаватель получает необходимые права проверки.

Студенту запрещены операции удаления репозитория, изменения системных Webhooks, управления участниками и снятия защиты служебных Git-ссылок.

## 8.3. Рабочие ветки

Предлагаемая структура:

- `main` — защищённый исходный вариант задания.
- `work` — рабочая ветка студента.
- `submission/1` — защищённый снимок первой сдачи.
- `submission/2` — снимок повторной сдачи.

Студент работает в своей ветке через привычный Git Workflow.

Системные ветки создаются серверной логикой и защищаются средствами Gitea.

При необходимости дополнительно создаются защищённые теги `submission-1`, `submission-2`, указывающие на тот же commit.

Защищённые ссылки нужны для того, чтобы студент не мог подменить уже сданную работу через force-push.

## 8.4. Сдача работы

Студент выполняет:

1. Clone.
2. Редактирование локального проекта.
3. Commit.
4. Push.
5. Нажатие «Сдать работу» в веб-платформе.

Простого Push недостаточно.

При нажатии «Сдать» backend:

1. Проверяет личность и права.
2. Проверяет дедлайн.
3. Проверяет существование удалённого commit.
4. Создаёт защищённый снимок сдачи.
5. Записывает SHA и номер попытки.
6. Подготавливает Code Review.
7. Переводит задание в Submitted.

Время определяется сервером. Время, записанное в Git-коммите на устройстве студента, не считается временем сдачи.

Операция должна быть повторяемой без создания дубликатов: повторный запрос после сетевого сбоя возвращает результат уже зафиксированной попытки.

Если создание Git-снимка или запись состояния не удались, система не должна сообщать об успешной сдаче. Ошибка отображается студенту, а частичная операция подлежит автоматическому согласованию.

## 8.5. Code Review

Для каждого зафиксированного снимка создаётся отдельный Pull Request относительно исходного задания.

Pull Request используется как интерфейс проверки. Автоматический merge не требуется.

Преподаватель может:

- Читать изменения.
- Просматривать файлы.
- Оставлять общий отзыв.
- Комментировать отдельные строки.
- Возвращать работу на исправление до дедлайна.
- Выставлять окончательный Pass / Fail.

Основная образовательная навигация остаётся частью Local GitHub. Функциональность полноценного PR использует глубоко интегрированную Gitea.

До реализации проверить на выбранной версии Gitea:

- Создание защищённого снимка.
- Создание PR.
- Общие комментарии.
- Inline-комментарии.
- Невозможность изменения снимка студентом.
- Невозможность обхода прав через прямой адрес Gitea.

## 8.6. Gitea Hardening

Начальная конфигурация должна отключать ненужные возможности:

- Самостоятельную регистрацию.
- Создание организаций обычными пользователями.
- Самостоятельное создание пользовательских репозиториев.
- Публичный каталог пользователей и ненужные публичные Explore-разделы.
- Gitea Actions.
- Ненужные репозиторные модули.

Все учебные репозитории приватные.

Системные API-токены не передаются в браузер.

# 9. ASSIGNMENTS & DEADLINES

## 9.1. Создание задания

Преподаватель указывает:

- Название.
- Описание.
- Стартовый проект.
- Назначенную группу.
- Дедлайн.
- Разрешение или запрет пересдачи.
- Автотесты при наличии.
- Видимость результатов автотестов.

Дедлайн определяется для конкретной публикации задания в группе.

Задание нельзя публиковать с дедлайном, уже находящимся в прошлом.

## 9.2. Статусы

- In Progress.
- Submitted.
- Revision Required.
- Passed.
- Failed.

## 9.3. Обычный дедлайн

Если студент ничего не сдал до дедлайна — Failed.

Если преподаватель вернул работу на исправление, но студент не отправил новую попытку вовремя — Failed.

Если работа была отправлена своевременно и ожидает проверки — Submitted сохраняется после дедлайна.

После дедлайна преподаватель может выставить только окончательный Passed или Failed.

Revision Required после окончания срока недоступен.

## 9.4. Пересдачи

Преподаватель заранее определяет, разрешены ли они.

При разрешённой пересдаче студент создаёт новые коммиты и повторно сдаёт работу до дедлайна.

Предыдущая попытка сохраняется как отдельный неизменяемый снимок.

После дедлайна обычная пересдача запрещена.

## 9.5. Push не равен сдаче

Платформа должна явно объяснять это студенту.

На странице задания отображаются:

- Состояние Git-репозитория.
- Состояние официальной сдачи.
- Время дедлайна.
- Предупреждение, если обнаружен Push, но работа ещё не отправлена.

Статус Passed / Failed не определяется одним лишь наличием коммита.

## 9.6. Время

В базе все временные метки хранятся в UTC.

В интерфейсе MVP отображаются по часовому поясу `Asia/Tashkent`.

Дедлайн 23:59 означает, что сдача доступна до окончания соответствующей минуты по времени сервера.

Проверка дедлайна и регистрация сдачи выполняются согласованно для предотвращения гонок между автоматическим Failed и запросом студента.

# 10. AUTOMATIC OUTAGE COMPENSATION

Это единственное согласованное автоматическое исключение из строгих дедлайнов.

## 10.1. Условия

Если подтверждённая недоступность веб-платформы или необходимого Git-сервиса пересекает момент окончания дедлайна и восстановление происходит после него, активируется механизм компенсации.

Система должна отличать подтверждённый сбой сервиса от отсутствия соединения на стороне отдельного студента.

## 10.2. Компенсация

После восстановления:

- У студента есть 24 часа для активации компенсации.
- При первом успешном авторизованном обращении к платформе запускается личное окно на 10 минут.
- Повторные входы и обновления страницы не сбрасывают таймер.
- В течение окна сдача временно разрешена.
- После завершения окна применяется обычная логика Passed / Failed.
- Если студент не воспользовался возможностью в течение 24 часов, компенсация истекает.

Для уже авторизованного пользователя первым обращением считается открытие или обновление защищённой страницы после восстановления. Повторный логин не требуется.

## 10.3. Техническая реализация

Для определения сбоя необходим независимый мониторинг доступности ключевых сервисов.

Нужно хранить:

- Начало и конец инцидента.
- Затронутые сервисы.
- Связанные дедлайны.
- Время восстановления.
- Выданные окна компенсации.
- Время активации каждым студентом.

Если доступность сервисов не восстановлена полностью, окно компенсации не должно запускаться.

Информация записывается в Audit Log.

Ручные индивидуальные продления для обычных случаев не входят в согласованный MVP.

# 11. GRADING

## 11.1. Стандартная модель

Только Pass / Fail.

Окончательное решение всегда принимает назначенный преподаватель, кроме автоматического Failed из-за пропущенного дедлайна.

## 11.2. Numeric Grading

Дополнительная шкала 1–5.

По умолчанию полностью отключена.

До включения Admin:

- Не показывается преподавателям.
- Не показывается студентам.
- Не принимает пользовательские запросы через API.
- Не влияет на Pass / Fail.

При выключении ранее сохранённые оценки не уничтожаются.

## 11.3. Академическая целостность

Пользователь не может оценить собственную работу, даже если одновременно имеет роль Owner/Admin.

Проверяются права на конкретное задание и отсутствие конфликта интересов, а не только наличие роли Teacher.

Изменения оценок фиксируются в Audit Log.

# 12. AUTOMATIC TESTS

## 12.1. Общие правила

Преподаватель может прикрепить автоматические тесты к заданию.

Если тестов нет — используется только ручная проверка.

Если тесты есть, они запускаются для конкретного зафиксированного снимка сдачи.

Итоговое решение Pass / Fail остаётся за преподавателем.

## 12.2. Видимость

Преподаватель выбирает:

- Visible — студент видит разрешённые результаты.
- Hidden — результаты видит только преподаватель.

При Hidden нельзя раскрывать исходники тестов, закрытые ожидаемые ответы, секреты и конфиденциальную информацию через логи или сообщения об ошибках.

## 12.3. Исполнитель

Для первой версии поддерживаем изолированный запуск Python-тестов.

Студенческий код не выполняется в процессе Next.js или непосредственно на основном хосте.

Исполнитель должен иметь:

- Ограничение времени.
- Ограничение CPU и памяти.
- Изолированную файловую систему.
- Запрет привилегированного режима.
- Отсутствие доступа к Docker Socket.
- Отсутствие доступа к секретам платформы.
- Отключённую внешнюю сеть по умолчанию.
- Очистку временных файлов после выполнения.

Интеграция полноценного Test Worker включается в запуск только после проверки его изоляции.

# 19. ПРИНЦИПЫ РЕАЛИЗАЦИИ SUPERPOWERS

После утверждения спецификации создаётся отдельный Implementation Plan.

Для каждой задачи необходимо определить:

- Конкретные файлы.
- Входные и выходные интерфейсы.
- Проверяемое поведение.
- Автоматические тесты.
- Команды проверки.
- Критерии завершения.
- Отдельный Git Commit.

Разработка по циклу:

1. Сначала тест, демонстрирующий требуемое поведение.
2. Проверка, что тест первоначально не проходит.
3. Минимальная реализация.
4. Повторное тестирование.
5. Review.
6. Commit.

Значимые изменения архитектуры во время реализации должны оформляться как изменение утверждённой спецификации, а не выполняться незаметно.
